# 部署架构与镜像策略说明 v0.1

> 回答三个部署问题：**要不要每个节点部署一份**、**Dashboard 是否随容器启动**、**采集与页面该不该拆成两个镜像**。
> 结论均以本仓库现有代码为依据，标注了对应的实现位置。

## 0. 先说结论

| 问题 | 结论 | 依据 |
| --- | --- | --- |
| 集群有很多台机器，要每台部署一个吗？ | **不要**。整个 K8s 集群只部署 **1 个副本**，中心化只读拉取 | 采集是 pull 模型，一次查询即覆盖全集群 |
| Dashboard 随容器启动吗？ | **是**。同一个 uvicorn 进程、同一个 8080 端口，没有独立 Web 服务器 | `app/main.py` 挂载 `frontend/dist` |
| 采集组件和 Dashboard 合成一个镜像还是拆开？ | **当前合为一个镜像**（all-in-one）；拆分的触发条件见第 4 节 | `deploy/Dockerfile` 多阶段构建 |
| 后续要暴露访问怎么封装？ | 仍是同一个镜像：容器内 `:8080` 同时提供页面与 API，用 Service / Ingress / `-p` 暴露即可 | 同源，无 CORS 问题 |

一句话：**它是一个"看板 + 分析器"，不是"探针"。** 监控数据由集群里已有的 Prometheus / ES / Jaeger / apiserver 产生，本工具只是这些数据的消费方，所以天然不需要贴着每台机器部署。

## 1. 为什么一台就够：pull 模型 vs push 模型

### 1.1 本项目不生产监控数据

```
node-exporter / cAdvisor ──► Prometheus        （集群已有）
fluent-bit / filebeat    ──► Elasticsearch     （集群已有）
OTel Collector           ──► Jaeger            （集群已有）
kubelet / controller     ──► kube-apiserver    （集群自带）
                                    │
                                    │  只读 HTTP 查询
                                    ▼
                            ai-ops-agent ×1
```

每轮检测实际只发出 **4 类只读请求**，全部是"整集群视角"，与节点数量无关：

| 数据源 | 实际调用 | 代码位置 |
| --- | --- | --- |
| Prometheus | `GET /api/v1/query_range` × 4 个指标模板 | `app/collectors/prometheus_adapter.py` |
| Elasticsearch | `_search`（日志规则 5 条） | `app/collectors/elasticsearch_adapter.py` |
| Jaeger | 按时间窗查 trace | `app/collectors/jaeger_adapter.py` |
| kube-apiserver | `GET /api/v1/events?fieldSelector=type!=Normal` | `app/collectors/k8s_adapter.py` |

指标查询本身已在 PromQL 侧做了 `avg by (namespace, pod)` 聚合（`app/collectors/queries.py`），返回的是**全集群所有 Pod 的序列**——一次请求，全量覆盖。

### 1.2 每节点部署一份会带来什么

| 维度 | 每节点一个 Agent | 中心化单实例（本项目） |
| --- | --- | --- |
| 部署单元 | DaemonSet，N 份 | Deployment，1 份 |
| 对 Prometheus 的压力 | N 倍重复查询 | 1 倍 |
| 告警 | N 条重复通知（同一故障） | 1 条，可聚合可升级 |
| LLM 调用成本 | ×N（同一根因被分析 N 次） | ×1 |
| 数据完整性 | 每个副本只有局部视图，Dashboard 看到的是碎片 | 全集群一个视图 |
| 状态存储 | N 个 SQLite，知识库/经验库分裂 | 1 份，可累积复用 |
| 扩缩容 | 加机器就要同步加副本 | 与节点数完全解耦 |

对"AI 诊断"这类场景，N 份副本还有一个致命问题：**同一个故障会被独立诊断 N 次、入库 N 份经验、推送 N 次告警**，反而制造噪音。

### 1.3 什么情况下才真的需要节点级 Agent

只有当"Prometheus 抓不到、只能在节点本地拿到"的数据才需要 DaemonSet，例如：

- 节点本地日志文件（容器 stdout 已被 fluent-bit 收走，不需要）；
- 内核态 / eBPF 级指标（node-exporter、Cilium 的职责）；
- 节点离线时的本地缓冲。

这些属于**采集基础设施**，不是本工具的职责。若将来要接入这类数据，正确做法是"新增一个采集器 DaemonSet 把数据推进 ES/Prometheus"，而不是把诊断逻辑铺到每个节点。诊断需要全局视野，恰恰不能分布。

## 2. Dashboard 确实随容器启动

镜像用多阶段构建，前端产物被直接打进运行镜像：

```dockerfile
FROM node:20-alpine AS frontend-build   # 阶段一：npm build
RUN npm run build                        #   → /build/dist

FROM python:3.11-slim AS runtime        # 阶段二：运行时
COPY --from=frontend-build /build/dist ./frontend/dist
CMD ["python", "-m", "app.main"]
```

`app/main.py` 在进程启动时完成三件事：

1. `app.mount("/assets", StaticFiles(...))` —— 挂载 JS/CSS 产物；
2. `GET /` 返回 `frontend/dist/index.html`，产物缺失时回退到一段提示页（`FALLBACK_HTML`）；
3. `lifespan` 里 `scheduler.start()` —— 检测循环随之启动。

所以 `docker run` 之后：

| 路径 | 内容 |
| --- | --- |
| `http://<host>:8080/` | Dashboard（Vue3 SPA） |
| `http://<host>:8080/api/*` | REST API（同一进程） |
| `http://<host>:8080/docs` | OpenAPI 文档 |
| `http://<host>:8080/healthz` | 健康检查（容器探针用） |

**没有 nginx，没有第二个容器，没有反代配置。** 前端调 `/api/*` 是同源请求，不存在跨域；鉴权靠 `auth_guard` 中间件统一拦截（`Authorization: Bearer` 或 `X-Auth-Token`）。

## 3. 关键组件清单：它们都在同一个进程里

| 组件 | 是否有独立进程 | 职责 |
| --- | --- | --- |
| Dashboard 静态资源 | 否（静态文件） | 页面渲染、人工确认入口 |
| FastAPI 路由 + 三角色守卫 | 是（主进程） | REST API、鉴权 |
| 检测调度器 | 否（asyncio task） | 每 10s 驱动一轮采集→检测→诊断→告警 |
| 采集适配器 ×4（×集群数） | 否（协程并发） | 只读拉取、失败重试 3 次后降级为空 |
| 检测引擎 | 否（进程内函数） | 阈值 / 3σ 基线 / 日志规则 |
| 编排器 + 4 个 Agent | 否（协程，45s 预算） | 指标、日志、链路分析 + 根因汇总 |
| 脱敏网关 | 否（进程内函数） | 外发前脱敏、残留扫描、fail-closed |
| RAG + 向量库 | 否（进程内） | 历史经验检索 |
| 告警策略 + 4 个渠道 | 否（进程内） | 5min 聚合、P0 不抑制可升级 |
| SQLite | 否（同进程文件访问） | 告警、诊断、知识、审计持久化 |

这里有个容易被忽略但很重要的设计点：**脱敏网关是进程内的一次函数调用，不是网络上的一个代理服务。** 敏感数据从采集到脱敏，全程没有离开过这个进程，不存在"先发给网关再外发"的网络跳点——这也是"敏感数据 100% 本地处理"这条硬约束在部署层面的保障。

## 4. 镜像策略：为什么现在是单镜像，什么时候该拆

### 4.1 当前选择：单镜像（all-in-one）

| 理由 | 说明 |
| --- | --- |
| **强生命周期耦合** | Dashboard 展示的每个数字都来自本进程的 SQLite 与内存状态。拆开就要额外引入服务发现、跨容器鉴权、CORS 配置，收益为零 |
| **体积几乎不增加** | 前端产物约 200KB（gzip 后不足 100KB），相对 `python:3.11-slim` 基础层可忽略；反过来单独搞一个 nginx 镜像要额外背 ~40MB 常驻 |
| **启动更快** | 单进程冷启动 < 2s，满足"启动 ≤5s"；双容器存在 nginx 先起、api 后起的竞态，需要额外探针编排 |
| **内存更省** | 单 uvicorn 空闲约 120MB，满足"空闲 ≤256MB"；再加一个 nginx 副本只会更紧张 |
| **契约原子性** | 前后端经常同步改（例如告警状态枚举、`statusLabel` 映射）。单镜像永远不会出现"新前端配旧后端" |
| **一条命令可交付** | `docker run` 即完整产品，正好匹配"用户拉下来就能用"的诉求 |

### 4.2 拆分镜像的触发条件

| 触发条件 | 拆分方式 |
| --- | --- |
| 单实例扛不住采集量（目标数过大 / 集群数过多） | 采集器独立为 Deployment（一个集群一个），API 无状态多副本 |
| 前端需要独立发布节奏（CDN、独立前端团队） | 拆出纯静态 web 镜像，走 CDN / 独立 Ingress |
| 出现长任务（批量复盘、报告导出、模型评测） | 拆出 worker 镜像，用队列消费 |
| 需要多副本 HA | API 与采集分离是前提，见 6.2 |

拆分后的形态应是 **3 个镜像**而不是 2 个：

```
web      : 静态资源 + 反代（仅当前端要独立时存在）
api      : FastAPI，无状态，可多副本，读写 PG
collector: 采集 + 检测 + 编排，按集群分片，每片 1 副本（选主）
```

判断标准很简单：**拆分的目的是"独立扩缩或独立发布"，而不是"看起来更像微服务"。** 当前阶段两者都不需要，所以不拆。

## 5. 数据流向：一次故障从发生到告警

```
① 生产（集群已有基础设施，不属本项目）
   工作节点: 业务 Pod → node-exporter / cAdvisor / fluent-bit / OTel
              │
              ▼
   监控后端: Prometheus  Elasticsearch  Jaeger  kube-apiserver
              │
② 拉取（ai-ops-agent 内，每 10s，4 路并发只读）
              ▼
   采集适配器 ──► 标准化事件（MetricEvent / LogEvent / TraceEvent / K8sEvent）
              │
③ 检测（进程内）
              ▼
   检测引擎（阈值 / 3σ 基线 / 日志规则）──► 异常事件 + 严重度
              │
④ 诊断（进程内并发 4 Agent，45s 预算）
              ▼
   指标 Agent / 日志 Agent / 链路 Agent  ──►  根因汇总 Agent
              │                                   ▲
              │                                   │ RAG 检索历史经验
⑤ 外发（唯一出口，必须先过脱敏）
              ▼
   脱敏网关（正则 + 规则 + 残留二次扫描，失败即阻断）
              │
      ┌───────┴────────┐
      │                │
   本地 Ollama      外部 DeepSeek（脱敏后文本）
⑥ 落地
      ▼
   告警策略（5min 聚合、P0 不可抑制、可升级）
      ▼
   飞书 / 钉钉 / 邮件 / Webhook
      ▼
   人工在 Dashboard 确认 ──► 写入经验库 + 知识库 ──► 反哺下一次诊断
```

要点：

- **② 是跨网络的唯一入口**（出站到集群内监控组件），**⑤ 是跨网络的唯一出口**（出站到 LLM 与告警渠道），中间全在进程内闭环；
- 采集失败不会阻断链路：单源重试 3 次后降级为空结果，其余数据源照常（`BaseCollector.safe_query`）；
- 诊断降级是有层级的：`unavailable()`（能力缺失）与 `skip()`（数据缺失）语义不同，不会把"没有 trace 数据"误报成"链路无异常"。

## 6. 部署形态

### 6.1 单机 `docker run`（最简单）

```bash
docker run -d --name ai-ops-agent -p 8080:8080 \
  -v $(pwd)/data:/data \
  -e MOCK_MODE=false \
  -e PROMETHEUS_URL=http://prometheus:9090 \
  -e ELASTICSEARCH_URL=http://es:9200 \
  -e OPERATOR_TOKEN=*** -e VIEWER_TOKEN=*** \
  ghcr.io/obc19/ai-ops-agent:latest
```

打开 `http://127.0.0.1:8080/` 即是 Dashboard。

### 6.2 K8s 集群内（`deploy/k8s/`）

清单按序号组织，`kubectl apply -f deploy/k8s/` 即可：

| 文件 | 内容 |
| --- | --- |
| `00-namespace-rbac.yaml` | Namespace + ServiceAccount + **只读** ClusterRole（events/pods/nodes，无写权限） |
| `10-config.yaml` | 多集群数据源 ConfigMap + 数据卷 PVC |
| `20-workload.yaml` | Deployment（`replicas: 1`、`strategy: Recreate`）+ Service |
| `30-ingress-networkpolicy.yaml` | Ingress + 默认拒绝的 NetworkPolicy |

凭据不从清单里写死，单独建 Secret：

```bash
kubectl -n aiops create secret generic ai-ops-agent-secrets \
  --from-literal=operator-token='***' \
  --from-literal=viewer-token='***' \
  --from-literal=llm-api-key='***'
```

**集群内免配置**：Pod 的 ServiceAccount Token 与 CA 会自动挂载，适配器自动读取
`/var/run/secrets/kubernetes.io/serviceaccount/{token,ca.crt}` 并直连 `https://kubernetes.default.svc`，
`clusters.yaml` 里只需填 Prometheus / ES / Jaeger 地址，`kubernetes_api_url` 留空即可。

访问方式三选一：

```bash
kubectl -n aiops port-forward svc/ai-ops-agent 8080:80   # 临时
# 或 Ingress：https://aiops.example.com
# 或 NodePort（不推荐暴露公网）
```

## 7. 能力边界（必须说清楚的两条）

### 7.1 目前只能单副本运行

`DetectionScheduler` 是**进程内单例**（`app/scheduler.py`），SQLite 也是单文件。多副本会：

- 同一时间窗口被 N 个副本各检测一次 → 重复诊断、重复告警；
- N 个进程同时写一个 SQLite → 锁冲突。

因此 Deployment 必须 `replicas: 1` + `strategy: Recreate`（`ReadWriteOnce` 卷不能两个 Pod 同时挂）。**这不是配置疏忽，是当前架构的显式约束。**

要做到多副本 HA，需要两步：状态外置到 PostgreSQL，调度加分布式锁（PG advisory lock 或 `coordination.k8s.io/Lease` 选主）。在此之前，可用性靠 K8s 的 Pod 自愈 + `restartPolicy` 保障（重启通常 < 3s）。

### 7.2 单实例的合理规模

一轮检测的数据量 ≈ `集群数 × Pod 数 × 4 指标 × 24 采样点`。

| 规模 | 建议 |
| --- | --- |
| ≤ 1000 Pod / 集群 | 开箱可用，保持 `DETECT_INTERVAL=10` |
| 1000 ~ 3000 Pod | 把 `DETECT_INTERVAL` 调到 30s，或按 namespace 收敛 PromQL |
| > 3000 Pod 或多集群 | 进入 4.2 的拆分路径：采集器按集群分片 |

存储侧同理：`RETENTION_DAYS` 默认 30 天，10Gi 卷对中等规模约可支撑数月，超出后按需扩容 PVC 或调小保留期。

## 8. 与硬约束的对应关系

| 约束 | 本方案如何满足 |
| --- | --- |
| 镜像 ≤ 300MB | 单镜像，`python:3.11-slim` + 静态资源，无 nginx |
| 启动 ≤ 5s | 单进程 uvicorn，无外部依赖预热 |
| 空闲 ≤ 256MB | 单进程 + SQLite，无额外常驻组件 |
| 检测延迟 ≤ 15s | 10s 周期 + 4 路并发拉取 |
| 诊断 ≤ 60s | `diagnosis_budget=45s` + 各 Agent 12s 超时 |
| 敏感数据 100% 本地 | 脱敏在进程内完成，唯一出口 fail-closed |
